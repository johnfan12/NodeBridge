# 重构范围与迁移

## 基线确认

2026-09-30 检查两个旧仓库，当前分支均为 `simple-tunnel-platform`。

现有 README 和运行代码的实际功能是账号控制台、节点状态/GPU 展示以及固定节点 SSH 穿透。父目录 AGENTS 的 Docker/GPU 实例、配额、卡时计费属于另一阶段的历史规划。NodeBridge 按用户确认的单程序双模式方案实现当前分支，不把历史规划标记为已迁移。

## 切换方法

1. 在 VPS 使用不同于旧服务的 Web 端口和 SSH 端口池部署 NodeBridge。例如旧版占用 `9999/7000/30000`，新版使用 `9443/30010–30019`。
2. 在一台节点安装 node 模式，使用旧服务相同的本地 SSH 端口 22 即可，两种转发可并行访问同一 sshd。
3. 通过配对接入，验证实际外网 SSH 登录、大文件传输、hub/节点重启恢复、GPU 状态和管理员权限。
4. 新建需要的控制台账号，保持节点已有 Linux 用户和 SSH 密钥。
5. 把正式入口切换到 NodeBridge；逐节点迁移。
6. 完成真实 VPS/节点验收后再停用旧 Python 和 FRP 服务。保留旧数据备份，用于回滚。

本次代码开发不改动旧仓库、不停用旧服务、不自动修改云防火墙、不把旧用户数据库当作已导入。

## v0.3.1 公告栏升级

从 v0.3.0 升级只需更新 hub，node 可以继续使用原版本。已有数据库自动兼容新增公告字段，无需迁移命令；原账号、节点、凭证、端口和暂停状态保留。公告尚未发布时首页不显示公告栏，管理员可在 `/admin#announcements` 发布第一条公告。

安装重启 hub 会断开现有 SSH 会话；发布与撤下公告只是更新数据库，不重启服务、不改变转发状态。公告与审计随 `hub.db` 一同备份。较旧二进制不认识公告字段，降级前请保留新版完整备份。

## Overleaf/TCP 迁移到 PortBridge

NodeBridge v0.2.0 曾包含额外 TCP 代理；从 v0.3.0 起分工调整为 NodeBridge 管理 SSH、[PortBridge](https://github.com/johnfan12/PortBridge) 管理 Overleaf/TCP。

1. 备份 NodeBridge hub/node 数据目录，记录旧代理名称、对应节点、本机目标端口、公网端口及暂停状态。
2. 在 VPS 安装 PortBridge hub（默认 HTTPS 9543、端口池 40000–49999），在原节点安装 PortBridge node（本地维护 9900）。它们可与 NodeBridge 同时运行。
3. 在 PortBridge 管理页面生成新配对链接，在节点使用 `portbridge pair` 配对。两种项目的链接和凭证不通用，不能直接复制数据库或配置文件。
4. 在 PortBridge 节点维护页授权原 Overleaf 本机端口，在 VPS 首页创建服务转发，先使用新的公网端口验证登录、上传与多人编辑。
5. 将 Overleaf 的站点地址和书签切换为新地址，确认正常后再升级 NodeBridge 到 v0.3.0。升级重启会断开经该服务的 SSH 连接，旧额外 TCP 转发也会停止；SSH 仍使用原端口。
6. 如需沿用旧 TCP 公网端口：先停止 NodeBridge 中原代理或升级至 SSH-only 版本，确保旧端口已释放；扩展 PortBridge 端口池后在创建转发时指定该端口。已创建的新端口代理需删除后重建，不会自动换端口。重建会断开该服务连接。

新 NodeBridge 不会激活旧 TCP 数据；旧配置的 `allowed_tcp_ports`/`tcp_forwarding_paused` 与 hub 的 `proxies` 元数据保留，仅用于人工迁移参考。不要直接降级到 v0.2.0，因为旧版本可能重新开放这些代理。回滚需停服、恢复升级前二进制和整套备份，并解决与 PortBridge 的端口冲突。
